# pre-visit-briefing

## Purpose

Provides an on-demand, natural-language pre-visit briefing for a single elevator, turning the unit's existing risk data (risk score/level, top prediction drivers, 6-day trend, last-visit recency, and the model explanation) into a short spoken summary with actionable recommendations. The text is generated by an Amazon Bedrock LLM with a deterministic fallback, exposed over HTTP, and read aloud in the browser via the Web Speech API. The briefing is generated on demand and never persisted.

## Requirements

### Requirement: Pre-visit briefing endpoint
The system SHALL expose `GET /api/elevators/{elevator_id}/briefing` that returns a natural-language pre-visit briefing for the unit. The response SHALL contain `elevator_id`, `text`, `source` (`"bedrock"` or `"fallback"`), and `generated_at`. The briefing SHALL be generated on demand and SHALL NOT be persisted.

#### Scenario: Briefing for an existing unit
- **WHEN** a client requests `GET /api/elevators/ELV-001/briefing` for an existing elevator
- **THEN** the API returns 200 with a non-empty `text` that references the unit's actual risk level/score and includes at least one recommendation
- **AND** `source` is set to `"bedrock"` or `"fallback"`

#### Scenario: Unknown unit
- **WHEN** a client requests a briefing for an elevator id that does not exist
- **THEN** the API returns 404 with `{"detail": "Elevator not found"}`

### Requirement: Briefing content reflects the unit's data
The briefing text SHALL be grounded in the unit's existing data — `risk_score`/`risk_level`, the top features, the trend direction, and last-visit recency — and SHALL adapt its length to the available signal (roughly 4–8 sentences for a data-rich in-scope unit, shorter when little signal is available). It SHALL end with one or two actionable recommendations.

#### Scenario: Data-rich in-scope unit
- **WHEN** a briefing is generated for an in-scope unit with a high risk score and clear prediction drivers
- **THEN** the text mentions the risk level, the main contributing factors, and a recommended action

#### Scenario: Out-of-scope unit
- **WHEN** a briefing is requested for a unit that is not in model scope
- **THEN** the text states that no model prediction is available and points to the last-visit notes instead of inventing risk detail

### Requirement: Briefing generated via Amazon Bedrock with configurable model
The system SHALL generate the briefing text by calling Amazon Bedrock through the Converse API. The model id and AWS region SHALL be configurable via environment variables (`BEDROCK_MODEL_ID`, `BEDROCK_REGION`), defaulting to `eu.amazon.nova-lite-v1:0` and `eu-north-1`. No AWS credentials SHALL be hard-coded; the backend SHALL authenticate via its IAM role/identity.

#### Scenario: Model is configurable without code change
- **WHEN** `BEDROCK_MODEL_ID` is set to a different supported model (e.g. `eu.anthropic.claude-haiku-4-5-20251001-v1:0`)
- **THEN** the briefing is generated with that model and the response parsing still succeeds, with no code change required

### Requirement: Deterministic fallback on Bedrock failure
WHEN the Bedrock call fails, errors, exceeds its timeout, or returns empty/blank text, the system SHALL return a deterministic briefing built from the unit's fields rather than an error, and SHALL set `source` to `"fallback"`. A valid unit SHALL never produce a 5xx response from the briefing endpoint due to a model failure. The system SHALL log the underlying cause at WARNING level before falling back, so a persistent fallback (e.g. missing IAM permission) is diagnosable from logs.

#### Scenario: Bedrock unavailable
- **WHEN** the Bedrock call raises an error or times out for an existing unit
- **THEN** the API returns 200 with `source: "fallback"` and a coherent briefing assembled from the unit's data

#### Scenario: Bedrock returns empty text
- **WHEN** the Bedrock call succeeds but returns empty or whitespace-only text
- **THEN** the API returns 200 with `source: "fallback"` and non-empty briefing text rather than an empty `"bedrock"` briefing

### Requirement: Briefing playback in the browser via Web Speech API
The unit detail view SHALL provide a "Brief me" control for in-scope units that fetches the briefing, displays its text, and reads it aloud using the browser Web Speech API (`speechSynthesis`), with a control to stop playback. The text SHALL always be shown so the briefing is usable without audio.

#### Scenario: Technician plays the briefing
- **WHEN** the technician clicks "Brief me" on an in-scope unit
- **THEN** the briefing text is displayed and read aloud
- **AND** a Stop control halts playback

#### Scenario: Speech synthesis unavailable
- **WHEN** the browser does not support `speechSynthesis`
- **THEN** the briefing text is displayed without error and no audio playback is attempted

#### Scenario: Fallback source indicated
- **WHEN** the briefing response has `source: "fallback"`
- **THEN** the UI shows a subtle indication that the briefing was generated without the model
