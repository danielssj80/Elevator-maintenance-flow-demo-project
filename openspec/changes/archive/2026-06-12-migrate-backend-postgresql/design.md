# Design: Migrate backend to PostgreSQL + SQLAlchemy

## Context

The backend currently serves a deterministic in-memory dataset (`app/data.py`, 100 elevators, `random.seed(42)`) through synchronous FastAPI handlers in `app/routers/elevators.py`, with all Pydantic models in a single `app/models.py`. Post-visit reports are validated and discarded. There is no test suite for the backend yet. The target architecture is already fully specified in `docs/backend-standards.md` (three layers, async SQLAlchemy 2.x, Alembic, PostgreSQL 16); this change implements it without altering the externally observable API except the report status code.

## Goals / Non-Goals

**Goals:**
- Durable storage in PostgreSQL with the read API contract preserved byte-for-byte.
- Three-layer backend (routers → services → repositories) with split ORM models and Pydantic schemas.
- Alembic as the only schema-change mechanism; idempotent deterministic seeding.
- Persist post-visit reports; return `201 Created` per API standards.
- Backend test suite (unit + integration) against a dedicated test database.

**Non-Goals:**
- AWS deployment (separate M3 task).
- Frontend changes (none expected; in scope only if standards/PostgreSQL adaptation requires it).
- ML model or retraining pipeline (M1) — reports are persisted, not consumed.
- `Technician`, `MaintenanceZone`, `TelemetryReading` entities; report read endpoints; authentication.

## Decisions

### D1 — Normalised tables for features and trend (vs JSONB columns)
`Feature[]` and `trend` become child tables (`elevator_features`, `elevator_trend_points`) as prescribed by `docs/data-model.md` §Current Data Storage. JSONB columns were considered (simpler mapping, fewer joins) but rejected: the data model doc already mandates the normalised layout, and child tables keep the door open for telemetry-grade querying later. Detail reads use `selectinload` to avoid N+1.

### D2 — `risk_level` stored but derived in the service layer
The column is kept for queryability, but the service recomputes `risk_level` from `risk_score` on every read (business rule: `>0.80` high, `0.50–0.80` medium, `<0.50` low). This honours "never stored independently from the score" while keeping the repository free of business logic.

### D3 — Report endpoint returns `201 Created`
Standards prescribe `201` for resource-creating POSTs. The frontend (`PostVisitReport.tsx`) does not inspect the status code, so the change is transparent. Deliberately accepted now (explicit user decision) instead of deferring a known contract fix. `ReportResponse` body shape is unchanged.

### D4 — Seeding as an explicit idempotent step at backend startup
The current generator moves to `app/seed.py`, preserving `random.seed(42)` for a reproducible dataset. The seeder runs on backend startup (after migrations, which run in the separate `migrate` compose service) and exits early if the `elevators` table is non-empty. Alternatives considered: seeding inside the migration (rejected — mixes schema with data, hard to evolve) and a manual CLI step (rejected — breaks "works on first `docker compose up`").

### D5 — Lists in `visit_reports` as JSONB
`components_replaced` and `parameters_corrected` are free-text string lists with no query requirements — JSONB columns suffice; a child table would be over-modelling.

### D6 — Test database strategy
Integration tests use a dedicated PostgreSQL test database (separate `DATABASE_URL`), with `app.dependency_overrides[get_db]` and per-test transaction rollback for isolation. SQLite in-memory was considered and rejected: JSONB and asyncpg behaviour must match production. Unit tests mock repositories with `AsyncMock` and need no database.

## Risks / Trade-offs

- [Response shape drift breaks the frontend silently] → Integration tests assert the exact JSON contract (field names and types) for both read endpoints against the seeded dataset.
- [Seeder races the `migrate` service] → Backend `depends_on` both `db` (healthy) and `migrate` (completed successfully); the seeder also fails fast if tables are missing.
- [Autogenerated initial migration misses details (server defaults, constraints)] → The migration is reviewed by hand before commit, per backend standards.
- [Latency regression on list/detail endpoints from real I/O] → Single query with eager loading; the dataset is small (100 rows), so no pagination is needed yet.
- [Docker dev loop slows down] → Named volume keeps data between runs; hot-reload volume mount is preserved for the backend.

## Migration Plan

1. Land the new persistence stack behind the same API on branch `feature/migrate-backend-postgresql`.
2. First deploy: `docker compose up` → `db` healthy → `migrate` applies the initial revision → backend seeds and serves.
3. Rollback: revert to the previous image; the in-memory implementation has no DB dependency. The `db` volume can be kept (harmless) or dropped.
4. No data migration is needed — the seed dataset is regenerable and no production data exists yet.

## Open Questions

None — the `200 → 201` question was resolved explicitly (do it now); all other decisions follow existing project standards.
