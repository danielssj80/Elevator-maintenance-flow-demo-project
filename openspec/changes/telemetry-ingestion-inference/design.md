# Design: telemetry-ingestion-inference

## Architecture

The change respects the existing three-layer backend split (routers → services → repositories) and adds one process outside it.

```
n8n (change 3)
  │  POST /api/telemetry/readings        POST /api/inference/run
  ▼
elevator-backend  ─────────────────────────────────────────────┐
  routers/telemetry.py     routers/inference.py                │
  services/telemetry_service.py                                │
  services/inference_service.py ──► services/inference_client.py
  repositories/telemetry_repository.py                         │  HTTP
  repositories/elevator_repository.py                          │
  app/ml/feature_mapping.py ◄── imported by backend/ml/generate_predictions.py
  │                                                            ▼
  ▼                                                    inference service
postgres                                                 POST /score
                                                         model.joblib
                                                         (no DB access)
```

`app/ml/feature_mapping.py` sits under `app/` deliberately: the Dockerfile's
`COPY app/ ./app/` already picks it up, so no Dockerfile change is needed, and
the offline script under `backend/ml/` imports *up* into it rather than the
runtime importing *down* into an offline directory.

## Key decisions

### The table is designed from the model, not from `docs/data-model.md`

`docs/data-model.md` documents a feature list — vibration, motor current, door
errors, door cycles — that no model in this repository consumes. The booster's
inputs are AI4I's seven columns (`generate_predictions.py:109`), and a grep for
the documented signals returns nothing outside that document.

`telemetry_readings` therefore stores, in human units:

| Column | Type | Feeds the model |
|---|---|---|
| `ambient_temperature_c` | float | yes → `Air_temperature__K` |
| `motor_temperature_c` | float | yes → `Process_temperature__K` |
| `motor_speed_rpm` | float | yes → `Rotational_speed__rpm` |
| `load_torque_nm` | float | yes → `Torque__Nm` |
| `motor_run_hours_cumulative` | float, nullable | yes → `Tool_wear__min` |
| `vibration_mm_s` | float, nullable | **no** — persisted, not consumed |
| `door_cycles` | int, nullable | **no** — persisted, not consumed |
| `door_errors` | int, nullable | **no** — persisted, not consumed |
| `motor_current_a` | float, nullable | **no** — persisted, not consumed |
| `source`, `batch_id`, `trace_id` | str | provenance |
| `recorded_at`, `ingested_at` | datetime | — |

Persisting the four unused signals is the honest resolution of the documentation
gap: the domain genuinely produces them, the current model genuinely ignores
them, and both facts are now written down in the same place. Fixing the stale
table in `docs/data-model.md` is a task in this change, not an afterthought.

`Type_L` / `Type_M` are a one-hot encoding of `building_type`, which is already a
column on `elevators`. They are derived in the service and deliberately **not**
stored: storing them would let a reading disagree with its own elevator.

### Kelvin is converted at one boundary and tested there

Readings are stored in °C, and `K = C + 273.15` is applied only while building
the feature matrix. This is the single highest-risk detail in the change: the
failure mode is not an exception but a fleet of identical, plausible scores. Two
independent guards, both written as tests that fail when the conversion is
removed: a unit test asserting `27.0 → 300.15` in the matrix, and a run-level
assertion that scored fleet variance is non-zero.

### Indexes, and what is deliberately deferred

Two indexes in the migration (`down_revision = 'aa3f0fc81e9c'`), written by hand
rather than autogenerated:

- `(elevator_id, recorded_at DESC)` — the window query the inference run issues
  once per elevator, and the read endpoint.
- `(recorded_at DESC)` — the retention prune and the staleness gauge.

At the change-3 ingest cadence of 15 minutes × 100 elevators ≈ 9,600 rows/day,
partitioning and BRIN are premature and are documented as deferred until roughly
50 M rows. `delete_older_than(days=30)` at the end of each run keeps a laptop
database bounded, which is the actual constraint here.

### A separate inference service, and dropping `shap`

`xgboost`'s own `Booster.predict(dmatrix, pred_contribs=True)` returns exact
TreeSHAP. That makes the `shap` package redundant and removes
`shap → numba → llvmlite` (~250 MB, the slowest import in the stack) from
`requirements-ml.txt`.

The model lives in its own image rather than in the backend:

- **Rejected — xgboost in the runtime image.** ~300 MB on an image deployed to a
  ~916 MB-RAM t3.micro, plus ~40 s of pip install on every CI PR, for a
  capability production never invokes.
- **Rejected — a pure-Python scorer.** Tree traversal is ~80 straightforward
  lines, but pure-Python TreeSHAP is ~150 lines of subtle EXTEND/UNWIND
  recursion and a prime source of silent divergence from the committed
  `predictions.json`. Kept as a documented escape hatch using Saabas attribution
  with an explicit "impact is approximate" note.
- **Rejected — a one-shot container.** No HTTP surface for n8n to trigger, no
  server span, no trace.

The separate service also earns a genuine three-service distributed trace
(`n8n → backend → inference → postgres`), so the observability work from change 1
justifies this architecture rather than being bolted onto it.

### The trend window shifts on date change, not per run

`ElevatorTrendPoint` carries `UniqueConstraint("elevator_id", "day_index")` and
the documented contract is six points with index 5 = today. A run may fire more
than once a day, so the window shifts on *date change*: overwrite index 5 if the
newest point is today's, shift and append otherwise. This is what makes an
on-demand demo trigger safe.

The shift is a DELETE of all six rows followed by an INSERT of six, inside the
run's transaction. The obvious `UPDATE ... SET day_index = day_index - 1` can
raise a duplicate-key violation on PostgreSQL even though the final state is
unique, because a non-deferrable unique index is checked per row and row order is
not guaranteed — it passes in testing and fails non-deterministically later. At
600 rows per run the delete-and-insert is trivially cheap.

### Production gating is a requirement, not a footnote

`docker-compose.prod.yml` auto-deploys on merge to `main`, and there is no
authentication anywhere in the codebase. Merging an ungated
`POST /api/telemetry/readings` would publish a write endpoint letting anyone
inject telemetry and re-score the live fleet. The routers are therefore not
registered when `deployment_environment == "production"`.

The follow-up, recorded here so it is not mistaken for an oversight, is an
`X-Ingest-Token` header compared with `secrets.compare_digest`, with `None`
meaning open in dev. It is a follow-up rather than weekend scope because gating
removes the exposure completely and a token adds configuration surface without
removing more.

### `httpx` becomes a runtime dependency

`httpx` is currently in `requirements-dev.txt` only — nothing under `app/`
imports it, and `opentelemetry-instrumentation-httpx` is installed against a
library the runtime image does not have. `inference_client.py` needs it, so it
moves to `requirements.txt` at the version dev already pins.

### The offline script's invocation changes

`generate_predictions.py` is documented as `python backend/ml/generate_predictions.py`
from the repository root, which leaves `backend/` off `sys.path`, so the new
`from app.ml.feature_mapping import ...` would raise `ImportError`. The
documented invocation becomes `cd backend && python -m ml.generate_predictions`,
updated in the module docstring and in `docs/backend-standards.md`.

## Out of scope

- **Frontend.** Nothing in this change touches `frontend/`. No response shape
  changes; the dashboard reads the same fields. The mandatory Playwright step is
  an explicit N/A.
- **n8n workflows.** The producer of these readings is change 3. This change is
  tested with curl and with the test suite.
- **Authentication.** Production gating only, per the decision above.
- **Retraining.** Post-visit reports still do not feed the model; the change
  scores with the committed booster and does not retrain it.
- **Production deployment of the inference service.** Dev compose only;
  `docker-compose.prod.yml` is untouched.
